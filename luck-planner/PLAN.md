## 1. Key architectural decisions (ADR)

| # | Decision | Rationale |
|---|---------|-----------|
| **ADR-1** | **The dashboard (2D and 3D) is a separate web application (React + TypeScript), served by the plugin's HTTP server on `127.0.0.1` and opened in the Paseo workspace browser** (`navigation.openBrowser`), with a fallback to `openExternalUrl`. The native RN panel is an overview layer that works everywhere (including mobile clients). | The plugin's client code is React Native: DOM, canvas, WebGL, `react-native-svg`, and DOM libraries are **forbidden** (reference.md → Cross-platform rules; tsconfig without DOM). React Flow / Cytoscape / Three.js physically cannot be embedded in the panel. Precedents in the same repo: bunny-search opens its web UI in a Paseo tab; memory-flash runs an HTTP server in the daemon process. The workspace browser is Electron Chromium → WebGL is available for 3D. |
| **ADR-2** | **The store is a single SQLite file** `$PASEO_HOME/plugins/luck-planner/luck-planner.db` (node:sqlite, Node ≥ 24.20), WAL, `busy_timeout` 5 s + write-retry, FTS5 (porter unicode61), the `meta.schema_version` table + migrations. All records are scoped via `project_key` (the canonical path of the workspace/project). | A direct requirement of the customer ("use SQLite as the store", "FTS5 and enhanced search, example — memory-flash"). A single file with `project_key` is simpler than one file per project and follows the proven memory-flash design. The lesson from memory-flash 0.3.2 (concurrent writers: busy timeout + retry) is carried over immediately, not after a lost write. |
| **ADR-3** | **Agent access is a bundled stdio MCP server** (`dist/mcp-server.js`, esbuild), injected into every agent via `server.before("agent.create")` + `paseo-plugin.json` `mcp.entry` (revision-independent publication, as in memory-flash 0.7.x). Agents read/write the tree with the `luck_tree_*` tools. | The plugin's purpose is for coding agents to maintain the fact tree. The plugin's RPC is not directly accessible to agents; MCP is the only channel. Proven mechanics from memory-flash/bunny-search. |
| **ADR-4** | **2D — React Flow** (custom nodes, edges, zoom/pan, fitView). **3D — @react-three/fiber + drei + d3-hierarchy** (the last block of stages). Both dashboard views live on a **shared data layer** (the same JSON API + graph model adapter + shared details panel), with a 2D/3D switcher in the toolbar. | Matches both customer documents: the 2D doc recommends React Flow, the 3D doc — react-three-fiber for the "trunk/branches/leaves/bees" metaphor. The shared data layer eliminates logic divergence between the views and makes 3D a clean renderer replacement. |
| **ADR-5** | **The tree in SQLite is an adjacency list** (`parent_id`) + kind enum (`root\|trunk\|branch\|subbranch\|leaf`), without a materialized path. For dashboard layout the tree is assembled in memory with a single query. | Flexible node moves without recalculating paths; the data volume (thousands of nodes) does not require a materialized path; layout is done on the dashboard side. |
| **ADR-6** | **Leaves use a state machine of statuses** from the customer's structure: `draft → ready → claimed → in_progress → (blocked) → done`, plus terminal `cancelled / superseded`. Each transition increments `revision` and writes an append-only audit (`who, when, what, with what result` — a mandatory customer requirement). | The state machine + revisions are the heart of "plan/fact". The audit is written starting from the first CRUD stage (B3), then only read. |
| **ADR-7** | **High-level goals have an approval gate**: `draft → proposed → approved` (approved by a human via the native panel; under orchestration/subagents — by the managing agent). Only `approved` is materialized into sub-branches with leaves. | Customer requirement: "they enter the project Tree only after the agreed plan is approved". The Plandex review gate precedent from the TEMP doc. |
| **ADR-8** | **Dashboard v1 is read-only**. All mutations (leaf statuses, goals) go through MCP (agents) or the native panel (human). Editing directly from the dashboard is on the roadmap. | Narrows the attack surface of the HTTP layer and keeps the first release clean; the API is only needed for reading anyway. |
| **ADR-9** | HTTP server: only `127.0.0.1`, a per-installation access token in the URL (precedent of memory-flash API keys), `GET /health`, SPA served from `dist/dashboard`. No binding to `0.0.0.0` without explicit configuration. | The plugin is trusted code with machine access; we do not expand the attack surface with a cheap binding. |
| **ADR-10** | **Plain is the third dashboard view and the default view** (block K): a card board in the spirit of "kanban rotated 90° counter-clockwise" — horizontal zones top to bottom: **PLAN** (high-level goals/plan, not implemented), **ACTIVE** (approval/review/implementation), **DONE** (completed/worked through); inside the zones — collapsible breakdowns by statuses and tree sections, cards; clicking a card opens a modal window with the maximum of information (the content reuses the details panel). The data is the same `/api/tree`, no new API is needed. | Customer requirement "the goal must be visible first"; plain works without WebGL and is cheaper than the diagram on large trees (expandable zones instead of a hairball); the breakdown is pure functions over the same payload, so the three views do not diverge in data. |

## 3. Data model (schema v1, draft)

```sql
-- Tree nodes: root(tech stack) → trunk → main branches → sub-branches → leaves(facts)
CREATE TABLE nodes (
  id TEXT PRIMARY KEY,             -- uuid
  project_key TEXT NOT NULL,       -- canonical project path
  parent_id TEXT REFERENCES nodes(id),
  kind TEXT NOT NULL CHECK (kind IN ('root','trunk','branch','subbranch','leaf')),
  name TEXT NOT NULL,
  description TEXT DEFAULT '',
  status TEXT NOT NULL,            -- for leaf: draft|ready|claimed|in_progress|blocked|done|cancelled|superseded
  version TEXT DEFAULT '',         -- fact/code version
  revision INTEGER NOT NULL DEFAULT 1,
  payload TEXT DEFAULT '{}',       -- JSON: tech stack of the root, file/function for branches, plan/fact for a leaf
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  created_by TEXT, updated_by TEXT,  -- agent id | 'user'
  archived_at INTEGER
);
CREATE INDEX nodes_project_parent ON nodes(project_key, parent_id);

-- Bees: links between leaves (influence), status + revision describe the influence
CREATE TABLE bees (
  id TEXT PRIMARY KEY, project_key TEXT NOT NULL,
  source_leaf_id TEXT NOT NULL REFERENCES nodes(id),
  target_leaf_id TEXT NOT NULL REFERENCES nodes(id),
  status TEXT NOT NULL, revision INTEGER NOT NULL DEFAULT 1,
  impact TEXT DEFAULT '',          -- degree/description of the influence
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  created_by TEXT, updated_by TEXT
);

-- Bugs: problems/incidents blocking a leaf/leaves
CREATE TABLE bugs (
  id TEXT PRIMARY KEY, project_key TEXT NOT NULL,
  title TEXT NOT NULL, description TEXT DEFAULT '',
  severity TEXT NOT NULL,          -- low|medium|high|critical
  status TEXT NOT NULL, revision INTEGER NOT NULL DEFAULT 1,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  created_by TEXT, updated_by TEXT
);
CREATE TABLE bug_nodes (bug_id TEXT REFERENCES bugs(id), node_id TEXT REFERENCES nodes(id),
  PRIMARY KEY (bug_id, node_id));  -- a bug can affect a group of leaves

-- High-level goals: formal description + broken-down plan; approval gate
CREATE TABLE goals (
  id TEXT PRIMARY KEY, project_key TEXT NOT NULL,
  formal_text TEXT NOT NULL,       -- task in natural language
  plan_json TEXT NOT NULL,         -- agent's plan: atomic steps
  status TEXT NOT NULL,            -- draft|proposed|approved|in_progress|done|cancelled
  materialized_node_id TEXT REFERENCES nodes(id),  -- subtree grown after approve
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  created_by TEXT, updated_by TEXT
);

-- Growth rates: goal → steps → facts; assigned to ANY element of the tree
CREATE TABLE growth (
  id TEXT PRIMARY KEY, project_key TEXT NOT NULL,
  subject_type TEXT NOT NULL CHECK (subject_type IN ('node','goal')),
  subject_id TEXT NOT NULL,
  steps_json TEXT NOT NULL,        -- [{step, state, facts[], reason}]
  status TEXT NOT NULL, revision INTEGER NOT NULL DEFAULT 1,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  created_by TEXT, updated_by TEXT
);

-- Append-only audit: who/when/what/result (mandatory requirement)
CREATE TABLE history (
  id INTEGER PRIMARY KEY AUTOINCREMENT, project_key TEXT NOT NULL,
  entity_type TEXT NOT NULL, entity_id TEXT NOT NULL,
  action TEXT NOT NULL,            -- create|update|status|link|approve|...
  revision INTEGER NOT NULL, actor TEXT,
  result TEXT DEFAULT '', at INTEGER NOT NULL
);

CREATE TABLE node_fts USING fts5(name, description, payload, content='nodes', content_rowid='rowid',
  tokenize='porter unicode61');   -- + INSERT/UPDATE/DELETE triggers (memory-flash pattern)
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);  -- schema_version
```

Leaf statuses are exactly as in the customer's structure. `history` is populated starting from stage B3 — without exceptions.

**D4. Registration of the MCP server in agents' config files** ✅ → `0.30.0` (Qwen Code added — `0.32.1`)
- Registration of `luck-planner` in the agents' **own config files**: OpenCode (`~/.config/opencode/opencode.json|jsonc`, `mcp` format), Kilo (`~/.config/kilo/kilo.jsonc|json`, same format), Cline (`~/.cline/data/settings/cline_mcp_settings.json`, `mcpServers` + `transport`), Cursor (`~/.cursor/mcp.json`, flat `mcpServers`), Qwen Code (`~/.qwen/settings.json`, flat `mcpServers` + `timeout` + `trust`), Codex CLI (`~/.codex/config.toml`, `[mcp_servers.luck-planner]` table). Buttons in the plugin settings — one per agent and "for all"; **nothing is written without an explicit request**: these files change the behavior of all agent sessions on the machine, so the decision stays with the human.
- Why: Paseo injects the server into an agent *session*. OpenCode/Kilo keep session registrations in memory per-directory and evict an idle directory — the server and all its tools disappear along with it (`luck-planner_*` vanish for the rest of the agent's life, although the MCP server itself is healthy); Cline/Cursor/Qwen Code/Codex CLI do not connect session MCP servers at all — for them a config entry is the only path. A config-file entry survives eviction (the config is re-read on every location start). A second, subtle effect (the memory-flash lesson): after eviction the dead session entry still owns the name `luck-planner` and **shadows** the live config entry — therefore when a config entry is present, session injection is **skipped** (the `agent.create` hook, with a log entry), and injection remains a fallback where the config cannot be written.
- Write rules: foreign content is preserved (other keys, servers, tables, comments); a file that does not parse as plain JSON (a `//` comment, a syntax error) is **not overwritten** — the plugin reports the problem and leaves the file as is; writing is atomic (temp + rename) and preserves file permissions; for TOML only its own table is edited, everything else is byte-for-byte; paths are computed **on every call** (not on import), so they follow the environment.
- Acceptance ✅ (by tests): `tests/agent-mcp-config.test.ts` (26: the format of each of the six agents; foreign keys/servers/tables/comments survive both registration and removal; a broken file is not overwritten; repeated registration changes nothing, Codex keeps exactly one own table; the status is truthful — registered / registered with an old command / not registered / agent not on the machine; provider coverage includes skipping session injection; writing is atomic — no temp files left, file permissions preserved; paths lead where the agent reads: XDG for OpenCode/Kilo, the home directory for Cline/Cursor/Qwen Code/Codex; Qwen Code: foreign settings of the file — `ui`, `modelProviders`, other MCP servers — survive registration, and the entry is removed wholesale; the `qwen-code` config provider is recognized, so session injection yields to the config entry). `tests/rpc.test.ts` — the RPC surface is extended with three D4 contracts. `typecheck` (both configs) + `vitest run` green (35 files, 602 tests).

**D5. Tree structure tools** ✅ → `0.31.0` (growth schema tolerant of array rewrites — `0.32.0`)
- Found via a test run (a live agent filled the tree with data of the session-manager plugin): the MCP surface could create **only leaves**. The store, however, could always do everything (`createNode` of any kind, `moveNode`, `archiveNode`), but the agent could neither create a trunk/branch nor rename the auto-skeleton (`Trunk` → `General`) nor move a fact to another branch — a project with several functional areas was described only as a flat list of leaves under a single `General` branch.
- Implementation: `luck_tree_upsert_node` (creation of a node of any kind `root|trunk|branch|subbranch|leaf`, or updating an existing one: name, description, version, payload, status), `luck_tree_move_node` (moving a node with its subtree; the store checks kinds and refuses a cycle), `luck_tree_archive_node` (soft deletion of a node with its subtree: rows remain in the DB, the audit trail keeps them, the tree stops showing them). The default parent is the first kind-compatible node (trunk → root, branch → first trunk, leaf → first branch), so the agent does not need to know the skeleton ids. The agent's skill (`server/skill.ts`) now explains the structure: "first shape the project, then fill it".
- Acceptance ✅ (by tests): `tests/mcp-tools.test.ts` (+8: creation of trunk/branch/subbranch; renaming the auto-skeleton; default parent; refusal of an impossible shape with a readable reason; requirement of `kind`/`name` on creation; move with a subtree; refusal of a kind-violating move; archiving a node with a subtree — the live tree stops showing them while the rows remain in the DB; inability to touch someone else's project). `tests/mcp-server-e2e.test.ts` and `tests/readme.test.ts` — the tool lists are extended. `typecheck` (both configs) + `vitest run` green (34 files, 586 tests).
- Refinement `0.32.0` following a live test run: **the growth schema is tolerant of array rewrites** — the Kilo client rewrites an array inside a schema-free object (`steps[].facts` arrives as `{"item": [...]}`, an empty one as `""`), and zod rejected the whole call. The data is not corrupted, only the shape is, so the array is normalized *before* validation (`lenientStringArraySchema`): an object with `item` → its array, a string → an array of strings, everything else is still rejected. Tolerance is introduced in the shared schema (`shared/growth.ts`) — meaning it works for the MCP path, the HTTP API, and the store.

### Block H — Live data

**H1. SSE + cache invalidation** ✅ → `0.24.0`
- `/api/events`: a `tree-changed` event after any write (store → event bus → SSE); the dashboard listens and refetches the changed subtree. In the native panel — TanStack Query invalidation on the same events (RPC polling or subscription).
- Acceptance: an e2e scenario — a leaf status is changed by an MCP tool, the dashboard and the panel update without a manual refresh.
- Implementation: the key decision — **not a hook on `store.write`, but polling of the journal**. Agents write via the MCP server, a *different process* with its own connection to the same SQLite (ADR-3), so an in-process hook would see only panel mutations and silently lose all agent writes — exactly the acceptance scenario. What the processes share is the file, and each mutation writes exactly one row to `history` (the B3 rule), so `server/change-feed.ts` polls `history.id > watermark`: an indexed read by primary key. `ChangeFeed` (start/stop, `unref` timer, debounce of own ticks, stop after 3 consecutive failures, grouping by project), `readChangesSince` — batched draining with an honest watermark (never ahead of already delivered rows, repair of a "drifted" cursor after DB recreation), `groupByProject`. `store`: `latestHistoryId()` + `listChangesSince()` (read-only). `http-server.ts`: the SSE stream remembers `?project=`, `broadcast(event, data, projectKey?)` wakes only its own tabs (several workspaces in the daemon), `ready` carries `{version, watermark}` — a reconnected tab sees what it missed. `http-lifecycle.ts` owns the stream: starts/stops it with the socket, provides `watermark` in `ready`. `shared/api.ts`: `readyEventSchema` + `treeChangedEventSchema` (the rows are the same `historyEntrySchema` as `/api/node/:id`) + `changesTouchNode` (the shared rule "this batch makes the node's view stale"). Dashboard: `dashboard/src/live.ts` (a clean module over an injected `EventSource`: parsing, coalescing a burst into one refetch, distinguishing reconnect from first open, self-healing on an unparseable payload), `api.ts.eventsUrl()`, `app.tsx` — refetch of the project and details panel, a `live/offline` indicator in the toolbar. **L8. Writing from the dashboard** ✅ → `0.48.0`
- An amendment to ADR-8: the browser gets exactly two decisions — a leaf status and a goal approval — not general writing. Routes `POST /api/node/:id/status` (`{status, expectedRevision?}`) and `POST /api/goal/:id/approve` (`{parentBranchId, expectedRevision?}`); no generic patch, create, move or archive.
- The order of checks in `handleRequest` is the security model: the token only from `Authorization` (a query-token opens the tab but does not write) → `POST` → `Origin`.host == `Host` (`sameOrigin`) → `Content-Type: application/json` → body ≤ 16 KiB (`413`).
- `expectedRevision` is checked **in the store, inside the transaction**: `StaleRevisionError` (`entityType`/`entityId`/`expected`/`current`) → `409` with `currentRevision`; in `approveGoal` the check stands before the early return "already approved". Optionality preserves the contract of MCP tools and the panel (additive). Actor — `UI_ACTOR` (`"user"`).
- After a write the server itself broadcasts `tree-changed`: the watermark before (`latestHistoryId`), `listChangesSince` after, a project filter, `broadcast`.
- Dashboard: `DashboardApi.post()` (the token in the header, `Content-Type`), `setLeafStatus`/`approveGoal`, `DashboardWriteConflict` (409 → refetch and a status line "moved elsewhere", not a request to press again); in the panel and the modal — buttons only according to `LEAF_TRANSITIONS[node.status]`, in the goal modal — *Approve under <branch>* when `canApproveGoal`.
- Acceptance (by tests): `tests/optimistic-write.test.ts` (6: stale/matching/absent for both methods, "nothing written and nothing audited" on refusal, the error names expected/current, a stale approval does not grow the plan a second time) + 8 write tests in `tests/http-server.test.ts` (happy path with an audit row and `user`, 409 without changing the row, header-only token, foreign/absent `Origin`, non-JSON, 405/404/400, broken/without a project/huge body, approval with materialization, broadcast) + markers in `tests/dashboard-build.test.ts`. `typecheck` + `vitest run` green (50 files, 882 tests).

**L9. Keyboard navigation in 2D** ✅ → `0.49.0`
- `dashboard/src/keyboard.ts` (new, clean — without React/DOM/SDK, like `graph.ts`/`plain.ts`): `NavBox`, `navBoxes` (the size is taken from `LAYOUT`, not from the DOM — the rule is tested on numbers), `readingOrder` (top to bottom, then left to right; sorting by id makes the order stable for a shuffled payload), `nearestInDirection`, `navTarget` (arrows + `Home`/`End`), `tabStopId`, `KEYBOARD_HINT`.

**L10. Multiple roots** ✅ → `0.50.0`
- The forest model: `shared/roots.ts` (new, clean) — `ForestRoot`, `buildForest` (grouping of live nodes by root, counters, `orphanCount` — nodes without an ancestor in the payload), `rootIdOf` (with cycle protection), `forestIsSingleRoot`, `pickGoalParent`, `restrictToRoot`, `EMPTY_FOREST`. ## 6. Risks and validation spikes

| Risk | Mitigation |
|------|-----------|
| WebGL unavailable in the workspace browser on some client | Spike I1 — before writing the scene; fallback to 2D with an explanation |
| React Flow degrades at >1000 nodes | Collapse/expand by default (G2), filters, a measurement on synthetics in G2's acceptance |
| The 3D bundle bloats the first chunk | A separate lazy-entry `dashboard-3d.js` (I1), loaded only on the switch |
| Concurrent access to SQLite (agents + UI + HTTP) | WAL + busy timeout + write-retry from stage B2 (the memory-flash 0.3.2 lesson), one DB-owner process |
| A plugin update breaks the agents' MCP path | Revision-independent entry publication from stage D2 (the memory-flash 0.7.1 lesson) |
| The HTTP layer as a vector | 127.0.0.1 + token + read-only API (ADR-8, ADR-9) |
| Mobile clients without a workspace browser | The native panel works everywhere; the dashboard — openExternalUrl; 3D on mobile — best-effort, the limitation is recorded in the README |
| Plain-view zone mapping "wrong" according to the actual visual inspection | Zones are data in `plain.ts` (`zoneFor*`), the adjustment is a change to the mapping table, not the module structure (the K3 decision) |
| Plain as the default changes the familiar "2D opened" | An explicit view choice is preserved in URL/localStorage and respected; buttons of all three views are always visible in the toolbar |

## 7. Rules for all stages

1. One stage = one commit; the code is written according to `__doc.md`, not from memory.
2. Types/contracts — only in `shared/` (zod), the SDK import boundaries are observed (including type-only imports).
3. Every test — on a real artifact (a file DB, a real MCP spawn, a real HTTP port), as in memory-flash. No mocks where they can be avoided.
4. Manual acceptance of the UI — mandatory (theme, compact, a clean browser console), `npm run typecheck` + `vitest run` — green before the commit.
5. `README.md`, `__doc.md` and this `PLAN.md` are all in English (per the project rules), as are the neighboring planning files.
